# Explicit capability and release limitations

Do not interpret unavailable values as zero. No random or fixture metrics are served by the production application.

- Host/process metrics are real psutil and systemd data. Status/player capacity/version use the Java status protocol, supported by both discovered servers. TPS and JVM heap internals need server-specific plugins/JMX and currently display as unavailable. Per-player ping is not available through vanilla RCON. Online status text and saved UUID/op/whitelist/ban records are available independently.
- File manager supports folder creation, text creation/edit, syntax preview, atomic validated JSON/YAML writes, snapshots, uploads/downloads, move/rename, single-file/empty-folder deletion, filename filtering, crash/log browsing. Worlds are read-protected from live download and write-protected from edits. Non-empty directories cannot be moved/deleted. `server.properties` is available through the redacted settings editor rather than raw upload/download. Secrets inside arbitrary third-party config file contents cannot be identified reliably; viewers should only be granted to trusted operators.
- Settings include existing supported properties and preserve comments. Version capability excludes simulation-distance for legacy Forge. Startup executable, arbitrary JVM arguments and heap changes remain read-only pending a reviewed systemd override; no unit is silently rewritten.
- Extension metadata supports plugin.yml, paper-plugin.yml, mcmod.info, mods.toml. Administrators can install a local JAR from Extensions into the server's `plugins/` or `mods/` directory after confirming they trust its source. Existing files cannot be overwritten, and a server restart is needed to load it. Automatic marketplace downloads, modpack upgrades/hot-swaps and incompatibility detection are not implemented.
- Existing backups use confirmed `.complete` markers. Archive inspection streams and validates gzip/tar, rejecting links and path traversal. It lists up to 5,000 members; archive validation may take minutes. Success dates/sizes/set count are available; exact backup duration is not inferred. Maintenance journal is shown. Retention editing is deliberately unavailable until the actual script is reviewed; the existing three-set retention remains authoritative.
- Restore is privileged. Four disposable fixture tests passed on Debian; actual service integration remains unverified. It validates/stages before stopping, retains the original tree by rename, restores ownership and ACLs, retains current RCON values, and restores previous service running state. Restart success means systemd accepted start, not that Minecraft finished startup. Minecraft readiness must be checked in console. Helper rollback snapshots are never pruned automatically. No real world has been restored as a test.
- Root helper shares the existing lock path, but compatibility with the maintenance script's actual locking semantics needs its root-only source review. Until reviewed, schedule restores outside maintenance windows and confirm maintenance is inactive.
- Journal console streams are authenticated and reconnect automatically. Metrics are sampled once every 3 seconds for all clients. Console uses one journal follower per open console, keeps 2,000 browser lines, supports ANSI/search/severity/scroll pause/export and command history. Very large journal messages can terminate a stream; reconnect remains available. Kernel-wide diagnostics are not exposed by default.
- Login brute force and mutating action limits exist. A reverse proxy connection/request limit is recommended for deployment to many users; this is a private LAN panel, not a publicly hardened multitenant hosting platform.
- Reboot recovery and full systemd/ACL/helper integration remain unverified until installation. Production deployment is not complete until those checks pass. See VALIDATION.md.
